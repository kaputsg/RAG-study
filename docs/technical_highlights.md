# RAG-study 项目技术亮点总结

这份文档按模块总结 RAG-study 的技术亮点，用于面试、作品集和复盘。表达原则：具体、真实，不使用夸张包装。

---

## 1. API 调用层

**做了什么**

封装 DeepSeek API 调用，统一处理请求参数、环境变量读取、异常和重试。

**为什么要做**

把模型调用从业务流程中拆出来，避免 RAGService 直接关心 HTTP 请求细节。

**项目里对应的价值**

后续如果更换模型服务或调整 prompt，只需要集中修改模型调用层。

**面试时怎么讲**

我没有在接口里直接写模型请求，而是把 DeepSeek 调用封装成独立模块，方便维护和定位错误。

---

## 2. RAG 检索层

**做了什么**

通过 RAGService 串联问题接收、向量检索、阈值过滤、上下文拼接和模型生成。

**为什么要做**

RAG 流程包含多个步骤，如果散落在 API 里会难以维护。

**项目里对应的价值**

让 `/ask` 接口保持清晰，也让检索和生成逻辑更容易调试。

**面试时怎么讲**

RAGService 是项目的主流程封装，负责把“先检索、再生成”的逻辑组织起来。

---

## 3. Embedding 层

**做了什么**

使用 `BAAI/bge-small-zh-v1.5` 将知识库 chunks 和用户问题转换成语义向量。

**为什么要做**

RAG 需要根据语义相似度查找资料，不能只依赖关键词匹配。

**项目里对应的价值**

让系统可以围绕中文学习资料进行语义检索。

**面试时怎么讲**

BGE 负责把文本变成向量，问题和文档片段都经过同一个模型处理，才能在向量空间里比较相似度。

---

## 4. FAISS 向量存储层

**做了什么**

使用 FAISS 构建本地向量索引，并在用户提问时检索相似 chunks。

**为什么要做**

需要一个能保存向量并快速返回相似结果的本地检索工具。

**项目里对应的价值**

在不额外部署向量数据库的情况下，完成了 RAG 原型的核心检索能力。

**面试时怎么讲**

FAISS 在项目里不是生成答案的，它负责存向量和查向量；生成答案仍然由 DeepSeek API 完成。

---

## 5. 文档加载与 chunk 切分层

**做了什么**

读取本地 UTF-8 `.txt` 文档，按固定长度切分 chunks，并保留 source 和 chunk_index。

**为什么要做**

整篇文档太长且主题混杂，直接检索整篇不利于定位答案。

**项目里对应的价值**

提高检索粒度，同时让 sources 可以追踪到具体文件和片段。

**面试时怎么讲**

我当前使用固定长度切分，适合学习阶段；后续可以改成段落切分或语义切分。

---

## 6. FastAPI 接口层

**做了什么**

提供 `GET /`、`GET /health`、`POST /ask`、`GET /documents`、`POST /documents/upload`、`DELETE /documents/{filename}`。

**为什么要做**

把后端能力以结构化接口提供给前端和测试脚本。

**项目里对应的价值**

前端可以通过 API 完成问答和文档管理，也方便用脚本做接口测试。

**面试时怎么讲**

FastAPI 负责请求入口、参数校验、文件校验和响应返回，核心 RAG 逻辑仍然封装在后端服务模块里。

---

## 7. Vue 前端层

**做了什么**

使用 Vue 3 实现问题输入、问答提交、answer 展示、sources 展示、retrieval_info 展示、文档上传、列表和删除。

**为什么要做**

让 RAG 能力从后端接口变成可操作的用户界面。

**项目里对应的价值**

项目可以完整演示“用户提问 -> 后端检索生成 -> 前端展示依据”的流程。

**面试时怎么讲**

前端不是只做展示，还承担了文档管理交互和请求状态反馈。

---

## 8. 文档上传/删除管理

**做了什么**

支持上传 UTF-8 `.txt` 文档、查看文档列表和删除文档。

**为什么要做**

知识库不是固定写死的，用户需要能维护自己的资料。

**项目里对应的价值**

让 RAG-study 从静态问答脚本变成可交互的知识库问答应用。

**面试时怎么讲**

上传和删除后会触发索引重建，确保文件变化能反映到检索结果里。

---

## 9. retrieval_info 可解释性

**做了什么**

返回检索命中状态、最高分、来源数量、置信度等信息。

**为什么要做**

只看最终答案很难判断问题出在检索还是生成。

**项目里对应的价值**

帮助用户和开发者判断这次回答是否有足够依据。

**面试时怎么讲**

retrieval_info 不是准确率，而是对本次检索质量的辅助说明。

---

## 10. 日志系统

**做了什么**

记录问答日志，包括问题、回答和检索信息等内容。

**为什么要做**

RAG 系统需要通过历史问答分析失败案例。

**项目里对应的价值**

为后续评估、调参和问题排查提供数据。

**面试时怎么讲**

日志可以帮助我回看哪些问题检索不到、哪些回答来源不够好。

---

## 11. 评估脚本

**做了什么**

准备基础评估问题集和相关测试脚本，用来验证已知问题、未知问题、接口和索引行为。

**为什么要做**

RAG 项目不能只靠主观体验判断效果，需要有可重复的检查方式。

**项目里对应的价值**

能验证接口是否可用、已知问题是否命中、未知问题是否拒答。

**面试时怎么讲**

评估脚本还比较基础，但已经让我开始用测试问题来观察检索质量。

---

## 12. FAISS 索引持久化

**做了什么**

将 FAISS 索引和 chunks 信息保存到本地，后端启动时优先加载已有索引。

**为什么要做**

避免每次启动都重新生成全部 embedding 和索引。

**项目里对应的价值**

减少重复计算，体现运行效率意识。

**面试时怎么讲**

持久化解决的是重启后的重复构建问题，但必须配合变更检测避免索引过期。

---

## 13. manifest 变更检测

**做了什么**

记录知识库文件状态，启动时判断当前知识库和索引对应的文件状态是否一致。

**为什么要做**

只加载持久化索引可能导致旧索引和新文件不一致。

**项目里对应的价值**

在知识库未变化时复用索引，在变化时自动重建索引。

**面试时怎么讲**

manifest 是索引一致性的检查机制，避免加载过期索引。

---

## 14. Docker 后端容器化

**做了什么**

使用 Dockerfile 和 docker-compose 完成 FastAPI 后端容器化初步实现。

**为什么要做**

减少后端运行环境差异，方便本地复现启动流程。

**项目里对应的价值**

体现部署准备意识，但不代表项目已经正式上线。

**面试时怎么讲**

我目前只 Docker 化了后端，没有做前端 Nginx、HTTPS、域名、监控和正式发布流程。

---

## 15. 文档与演示材料

**做了什么**

整理 README、部署文档、Docker 文档、演示脚本、项目讲解、简历描述、社交平台文案和面试问答。

**为什么要做**

项目不仅要能运行，也要能被别人快速理解和复现。

**项目里对应的价值**

方便老师验收、面试官查看和自己后续复盘。

**面试时怎么讲**

我把开发结果整理成文档，是为了让项目从代码练习变成可展示、可复盘的作品。
