# RAG-study 第二阶段规划

## 1. 第二阶段目标

第二阶段的目标是在 v1.0 本地 RAG 原型基础上，继续提升文档格式支持、检索质量、交互体验和部署能力。

第二阶段不是把项目包装成完整产品，而是在保留当前清晰边界的前提下，逐步补齐更常见的 RAG 应用能力。

## 2. 为什么不继续在 v1.0 里无限加功能

v1.0 的目标是完成第一阶段闭环：本地知识库、RAG 问答、前后端对接、文档管理、日志评估、索引持久化、Docker 后端容器化和文档收尾。

如果继续在 v1.0 里不断加功能，会带来几个问题：

- 版本边界不清楚，难以判断阶段是否完成。
- 新功能可能引入新的不稳定点，影响演示。
- 项目总结和面试表达会变得混乱。
- 学习节奏容易从“完成闭环”变成“无限堆功能”。

因此 v1.0 应该先收尾，第二阶段再有计划地扩展。

## 3. 优先级 P0 / P1 / P2 规划

| 优先级 | 方向 | 说明 |
| --- | --- | --- |
| P0 | 文档格式扩展 | 先解决知识库输入来源过窄的问题 |
| P0 | PDF / Word / Markdown 支持 | 让项目能处理更常见的学习和工作文档 |
| P1 | rerank 重排序 | 提升检索片段质量 |
| P1 | 流式输出 | 改善回答体验 |
| P1 | 对话历史 | 支持基础多轮问答 |
| P1 | 前端 UI 优化 | 提升演示效果和可用性 |
| P2 | 数据库存储 | 保存问答记录和元信息 |
| P2 | 用户登录和权限 | 为多用户隔离做准备 |
| P2 | 云服务器部署 | 从本地运行走向可远程访问 |
| P2 | Nginx + HTTPS | 完善基础部署链路 |
| P2 | RAG + Agent 工具调用 | 探索更复杂的工具调用能力 |

## 4. P0：文档格式扩展

v1.0 目前只支持 UTF-8 `.txt` 文档。第二阶段最优先的方向是扩展文档解析能力，让知识库可以接入更多真实资料。

重点目标：

- 保留现有 txt 支持。
- 增加统一的文档解析入口。
- 将不同格式解析成统一文本结构。
- 解析失败时给出明确错误提示。

## 5. P0：PDF / Word / Markdown 支持

计划支持的格式：

- PDF：用于论文、课程资料、说明文档。
- Word：用于报告、简历、项目文档。
- Markdown：用于技术笔记和仓库文档。

注意：这些能力不属于 v1.0 已实现范围，第二阶段需要单独开发和测试。

## 6. P1：rerank 重排序

当前检索主要依赖向量相似度。第二阶段可以在初步召回后加入 rerank，对候选片段重新排序。

预期收益：

- 提高最终进入上下文的片段质量。
- 减少语义相近但实际不相关的结果。
- 为后续评估指标优化提供基础。

需要注意：

- rerank 会增加接口耗时。
- 需要选择合适的 rerank 模型或服务。
- 需要用评估问题集验证效果，而不是只凭感觉判断。

## 7. P1：流式输出

流式输出可以让前端逐步显示模型回答，减少用户等待感。

计划内容：

- 后端支持流式响应。
- 前端逐步渲染回答内容。
- 保留错误处理和最终 sources 展示。

需要注意：流式输出会改变前后端交互方式，需要单独规划接口和 UI 状态。

## 8. P1：对话历史

当前项目主要是单轮问答。第二阶段可以加入基础对话历史，让用户围绕同一份知识库连续追问。

计划内容：

- 前端保留当前会话的问题和回答。
- 后端接收必要的历史上下文。
- 控制历史长度，避免上下文过长。

需要注意：对话历史不等于数据库持久化，前期可以先做单页面会话级历史。

## 9. P1：前端 UI 优化

当前前端能完成基本操作。第二阶段可以优化信息层次和演示体验。

优化方向：

- 问答区、文档区、检索信息区布局更清晰。
- sources 展示更适合阅读。
- retrieval_info 用更直观的方式呈现。
- 上传和删除状态更明确。
- 空状态和错误状态更友好。

## 10. P2：数据库保存问答记录

后续可以加入数据库，用于保存问答记录、文档元信息和评估结果。

可能方案：

- SQLite：适合本地学习和轻量原型。
- PostgreSQL：适合后续部署和更完整的数据管理。

第二阶段前期不建议直接上复杂数据库结构，应该先明确需要保存哪些数据。

## 11. P2：用户登录和权限

用户登录和权限系统可以让不同用户管理自己的知识库，但这会明显增加复杂度。

计划内容：

- 用户注册和登录。
- 用户级知识库隔离。
- 文档和问答记录按用户区分。

该能力不属于 v1.0，建议在文档格式、检索质量和基础数据库稳定后再做。

## 12. P2：云服务器部署

云服务器部署可以让项目从本地运行扩展到远程访问。

计划内容：

- 准备服务器环境。
- 配置后端服务运行方式。
- 构建前端静态资源。
- 配置环境变量和日志目录。

需要注意：正式部署前必须检查 API Key、跨域、安全配置和日志敏感信息。

## 13. P2：Nginx + HTTPS

如果要做远程演示，可以继续补充 Nginx 和 HTTPS。

计划内容：

- Nginx 反向代理后端接口。
- Nginx 托管前端静态资源。
- 配置 HTTPS 证书。
- 检查跨域和接口地址。

这属于部署增强，不是 v1.0 已完成能力。

## 14. P2：RAG + Agent 工具调用

在 RAG 链路稳定后，可以探索更进一步的工具调用能力，例如：

- 根据问题决定是否检索知识库。
- 调用评估脚本分析回答质量。
- 调用文档管理工具查询知识库状态。

这个方向更适合作为探索，不建议作为第二阶段最早目标。

## 15. 技术风险

- 多格式文档解析可能遇到乱码、表格、图片和复杂排版。
- PDF 解析质量不稳定，可能影响 chunk 质量。
- rerank 会增加延迟和资源消耗。
- 流式输出会改变接口和前端状态管理。
- 对话历史容易导致上下文过长。
- 数据库和用户权限会增加后端复杂度。
- 云部署涉及安全、环境变量、日志和域名证书配置。

## 16. 学习路线建议

建议按以下顺序学习和开发：

1. 先扩展文档解析，不急着动前端大结构。
2. 再优化 chunk 策略和评估问题集。
3. 然后尝试 rerank，用评估结果判断是否有效。
4. 再做流式输出和对话历史，提升体验。
5. 最后考虑数据库、用户权限和云部署。

这样可以保证每一步都有明确收益，也方便回退和复盘。
