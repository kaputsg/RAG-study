# RAG-study 项目面试问答

这份清单用于准备项目介绍、技术面试和答辩。每个问题包含“标准回答”和“口语版回答”：标准回答适合正式表达，口语版回答适合现场自然说明。

---

## 1. 这个项目是做什么的？

### 标准回答

`RAG-study` 是一个本地知识库 RAG 问答系统。用户可以在 Vue 前端输入问题，FastAPI 后端会从本地 `.txt` 知识库中检索相关文本片段，再调用 DeepSeek API 基于检索结果生成回答。系统还会返回引用来源，展示来源文件、`chunk_index`、相似度和片段内容。项目也支持上传和删除 `.txt` 文档，并在文件变化后重建 FAISS 索引。

### 口语版回答

我做的是一个本地知识库问答系统。它不是直接把问题扔给大模型，而是先从本地资料里找相关片段，再让模型根据这些片段回答。页面上还能看到引用来自哪个文件。后来我又补了文档列表、上传、删除和自动重建索引。

---

## 2. 什么是 RAG？

### 标准回答

RAG 是 Retrieval-Augmented Generation，中文叫检索增强生成。它将检索系统和大模型生成能力结合起来：先从外部知识库检索与问题相关的资料，再将这些资料作为上下文交给大模型生成回答。这样可以让回答更多地基于指定知识库，而不是只依赖模型训练时已有的知识。

### 口语版回答

RAG 可以理解成“先查资料，再回答”。大模型先拿到知识库里和问题最相关的内容，然后基于这些资料组织答案。

---

## 3. 你的 RAG 流程是什么？

### 标准回答

项目启动时，`DocumentLoader` 会读取 `data/knowledge_base/` 中的 `.txt` 文件并切分成 chunks。`VectorStore` 使用 `BAAI/bge-small-zh-v1.5` 为每个 chunk 生成 embedding，归一化后写入 FAISS 索引。用户提问时，问题也会被转换成 embedding，再通过 FAISS 检索相似 chunks。低于 `similarity_threshold` 的结果会被过滤。`RAGService` 将剩余 chunks 拼接成 context，调用 DeepSeek API，最后返回 `answer` 和 `sources`。

### 口语版回答

启动时先读文档、切片、向量化、建索引。提问时把问题也向量化，从 FAISS 里找相近片段，过滤掉分数低的结果，再把资料交给 DeepSeek 生成回答。最后把答案和来源一起返回前端。

---

## 4. 为什么要把文档切成 chunk？

### 标准回答

整篇文档可能过长，而且不同段落的主题不完全一致。如果直接对整篇文档生成一个向量，语义会被平均化，检索时不容易定位到具体内容。切成 chunks 后，可以在更细粒度上生成 embedding 和检索结果，也能减少传给大模型的无关上下文。

### 口语版回答

切片是为了让检索更精准。整篇文档太大，里面可能有多个主题。切成小段以后，系统更容易找到真正和问题相关的那一段。

---

## 5. chunk_size 和 chunk_overlap 怎么设置？

### 标准回答

当前项目使用固定长度切分，默认 `chunk_size=120`、`chunk_overlap=30`。`chunk_size` 过小会导致语义不完整，过大则会混入更多无关内容。`chunk_overlap` 用于保留相邻 chunks 之间的上下文，降低句子或段落刚好被截断的影响。实际项目中应该基于文档类型、检索效果和评测集调参。当前 API 初始化值与 `DocumentLoader.load_and_split()` 的默认值一致，后续可以进一步统一参数传递，避免配置分散。

### 口语版回答

我现在用的是每段 120 个字符，前后重叠 30 个字符。块太小容易丢上下文，太大又会带进无关内容。重叠部分主要是防止一句话正好被截断。正式优化时，我会用测试问题来调参数。

---

## 6. 为什么要保留 source 和 chunk_index？

### 标准回答

`source` 用于记录 chunk 来自哪个文件，`chunk_index` 用于标记它在原文切分结果中的位置。保留这两个字段可以追踪回答依据，在前端展示引用来源，也方便调试检索效果。当结果不准确时，可以快速定位到具体文档和片段。

### 口语版回答

这两个字段是为了可追踪。回答有问题时，我能看到它到底引用了哪个文件、哪一段，而不是只看到模型最后生成的一句话。

---

## 7. BGE embedding 在项目里做什么？

### 标准回答

项目使用 `BAAI/bge-small-zh-v1.5` 将文本转换为 embedding，也就是语义向量。知识库 chunks 和用户问题都会经过同一个模型转换。这样系统就能在向量空间中比较问题与文本片段的语义相似度，而不只是做关键词匹配。

### 口语版回答

BGE 的作用是把文字变成向量。问题和知识库片段都变成向量后，就可以比较它们语义上有多接近。

---

## 8. FAISS 在项目里做什么？

### 标准回答

FAISS 用于建立和查询本地向量索引。当前实现会对 embedding 做 L2 归一化，然后使用 `faiss.IndexFlatIP` 进行内积检索。向量归一化后，内积可以用于衡量余弦相似度。查询时系统会返回分数最高的候选 chunks。

### 口语版回答

FAISS 是本地向量检索工具。BGE 负责把文字变成向量，FAISS 负责把这些向量存起来，并在提问时快速找出最接近的片段。

---

## 9. 为什么使用 similarity_threshold？

### 标准回答

只取 Top K 不能保证结果一定相关。如果知识库中没有答案，FAISS 仍然会返回相对最接近的片段。项目通过 `similarity_threshold=0.65` 过滤低相关结果。如果过滤后没有结果，系统会直接返回无法找到相关信息，减少模型基于无关上下文生成答案的风险。

### 口语版回答

Top K 只是“最像的几个”，但不代表真的相关。所以我又加了阈值。分数太低就不要交给模型，宁可明确说知识库里没有找到。

---

## 10. 为什么上传文档后要重建索引？

### 标准回答

上传文档后，知识库内容发生变化。新文档如果没有被切分、向量化并加入索引，后续检索就无法找到它。当前实现选择全量重建：重新读取所有 `.txt` 文件、切分 chunks、生成 embeddings 并建立 FAISS 索引。对于学习项目，这种方式逻辑清晰；文档较多时应优化为增量更新。

### 口语版回答

文件上传成功不代表检索系统已经知道它。还要重新切片、向量化、建索引，新的资料才能被问到。我现在用全量重建，简单直观，后面数据多了再做增量更新。

---

## 11. 为什么删除文档后也要重建索引？

### 标准回答

删除文件后，如果不更新索引，原索引中仍可能存在该文档对应的向量，检索结果就会与当前知识库文件不一致。当前项目删除成功后会重新读取剩余文件并重建 FAISS 索引，确保已经删除的文档不再参与检索。

### 口语版回答

删文件后也要重建，不然索引里还可能留着旧片段，系统还能搜到已经删除的内容。文件和索引必须保持一致。

---

## 12. FastAPI 后端接口怎么设计？

### 标准回答

当前后端提供六个接口：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/` | 确认服务已启动 |
| `GET` | `/health` | 基础健康检查 |
| `POST` | `/ask` | 接收问题，返回 `answer` 和 `sources` |
| `GET` | `/documents` | 获取知识库 `.txt` 文档列表 |
| `POST` | `/documents/upload` | 上传 `.txt` 文档并重建索引 |
| `DELETE` | `/documents/{filename}` | 删除 `.txt` 文档并重建索引 |

请求和响应使用 Pydantic 模型定义。上传接口使用 `multipart/form-data`，并校验文件名、扩展名、UTF-8 编码和非空内容。删除接口会校验文件扩展名、文件存在性和目标类型。

### 口语版回答

我把接口分成三类：服务检查、问答、文档管理。问答走 `/ask`，文档列表走 `/documents`，上传和删除会在修改文件后重建索引。接口返回结构用 Pydantic 定义，前端处理起来比较明确。

---

## 13. 前端怎么调用后端？

### 标准回答

前端使用 Vue 3 和 Fetch API。后端基础地址来自 `VITE_API_BASE_URL`，默认值为 `http://127.0.0.1:8000`。问答接口发送 JSON 请求；上传接口使用 `FormData`；删除接口使用 `DELETE` 方法并对文件名执行 URL 编码。页面挂载后会自动请求文档列表，上传和删除成功后也会再次刷新列表。

### 口语版回答

前端用 fetch 调后端。提问时传 JSON，上传时用 `FormData`，删除时发 `DELETE` 请求。API 地址放在前端环境变量里，上传和删除成功以后都会自动刷新列表。

---

## 14. CORS 是什么，为什么要配置？

### 标准回答

CORS 是 Cross-Origin Resource Sharing，中文叫跨源资源共享。浏览器会限制不同源之间的请求。开发环境中，Vue 前端通常运行在 `localhost:5173`，FastAPI 后端运行在 `127.0.0.1:8000`，两者的端口不同，因此属于不同源。项目在 FastAPI 中配置了 `CORSMiddleware`，允许常见的本地前端地址访问后端。

### 口语版回答

前后端开发时端口不同，浏览器会把它们当成不同来源。如果后端不允许跨域，前端请求就会被浏览器拦下来。所以我在 FastAPI 里配了 CORS。

---

## 15. 项目怎么做错误处理？

### 标准回答

错误处理分为几层：

1. 配置层：程序启动时校验 `DEEPSEEK_API_KEY`，缺少配置会尽早报错。
2. 模型调用层：DeepSeek 客户端使用 tenacity 做指数退避重试，最多尝试 3 次，并对 API 异常和未知异常返回错误信息。
3. API 层：`/ask` 校验问题；上传接口校验扩展名、编码和内容；删除接口校验扩展名、文件是否存在和目标类型。异常会转换为适当的 HTTP 状态码和 `detail` 信息。
4. 前端层：页面展示 loading、上传中、删除中和 error 状态，避免用户不知道请求是否正在执行。

当前仍有改进空间，例如上传或删除后索引重建失败时，还没有实现文件操作回滚。

### 口语版回答

我不是只在前端弹一个错误。配置、模型调用、接口和页面四层都有处理。比如 Key 没配会在启动时报错；模型请求失败会重试；上传会检查格式、编码和空文件；前端会显示 loading 和错误。现在还缺少文件操作失败后的回滚，这也是后续优化点。

---

## 16. 这个项目现在有什么不足？

### 标准回答

当前项目定位是本地学习和演示系统，主要不足包括：

* 只支持 UTF-8 编码的 `.txt` 文档
* chunk 切分仍是固定字符长度，没有按段落或语义切分
* 上传和删除后采用全量索引重建，文档多时性能会下降
* FAISS 索引没有持久化，服务重启时需要重新构建
* 没有用户鉴权和权限隔离
* 文件更新与索引重建之间缺少事务和回滚机制
* 没有 rerank、混合检索和系统化评测集

### 口语版回答

它现在适合学习和展示，还不是生产系统。比如只支持 txt，每次改文档都全量重建索引，没有登录权限，没有索引持久化，也没有做更细的检索评测。

---

## 17. 如果知识库文档很多，现在这个方案有什么问题？

### 标准回答

文档增多后，主要问题是初始化和更新成本。当前实现每次启动、上传或删除都会重新读取全部文档、重新切分、重新生成 embeddings 并全量构建 FAISS 索引。文档规模较大时，耗时和资源占用都会明显增加。此外，当前使用 `IndexFlatIP` 做精确检索，数据量很大时也需要考虑更合适的索引结构、持久化方案和批处理策略。

### 口语版回答

现在的瓶颈是全量重建。文件多了以后，每次上传一个文档也要把全部内容重新向量化，成本会越来越高。数据再大一些，还要考虑持久化索引和更合适的 FAISS 索引类型。

---

## 18. 后续你会怎么优化这个项目？

### 标准回答

我会按优先级逐步优化：

1. 增加索引持久化和增量更新，减少启动与文档变更成本。
2. 引入文档 ID、chunk ID 和元数据存储，完善文件与索引的一致性管理。
3. 优化 chunk 策略，增加按段落或语义切分。
4. 增加关键词检索、向量检索和 rerank 组合，提高召回与排序质量。
5. 建立固定问答评测集，评估召回率、来源准确性和拒答效果。
6. 增加 PDF、Word、Markdown 等解析器。
7. 增加鉴权、日志、监控、Docker 和自动化测试。

### 口语版回答

我会先解决性能和一致性：做索引持久化、增量更新、文档 ID 和回滚。然后再提升效果，比如更好的切片、混合检索、rerank 和评测集。最后补更多文件格式、权限和部署能力。

---

## 19. 你怎么证明回答来自知识库而不是模型胡编？

### 标准回答

当前项目使用三层控制：

1. 检索阶段通过相似度阈值过滤低相关 chunks，没有合格结果时直接拒答。
2. Prompt 明确要求模型只基于提供的上下文回答，不要凭空编造。
3. 后端将检索结果作为 `sources` 返回，前端展示来源文件、`chunk_index`、相似度和原始片段，用户可以人工核对。

需要说明的是，仅靠 Prompt 和引用展示不能在理论上完全杜绝模型生成额外内容。更严格的系统还可以增加逐句引用、答案事实校验和自动评测。

### 口语版回答

我做了阈值过滤、限定上下文回答和来源展示。页面上可以展开原始片段，直接检查答案有没有依据。不过我不会说这样就百分之百杜绝幻觉。更严格的话，还要做逐句引用和事实校验。

---

## 20. 如果检索结果不准，你会怎么排查？

### 标准回答

我会按链路逐步排查：

1. 检查原始文档中是否确实存在答案，编码和读取是否正常。
2. 检查 chunk 切分结果，确认关键内容是否被截断或分散。
3. 查看返回的 `source`、`chunk_index`、`text` 和 `score`，判断是召回问题还是生成问题。
4. 调整 `chunk_size`、`chunk_overlap`、`top_k` 和 `similarity_threshold`。
5. 检查 embedding 模型是否适合当前中文语料。
6. 使用固定测试问题建立评测集，比较不同参数。
7. 如果仅靠向量检索仍不稳定，再考虑关键词混合检索和 rerank。

### 口语版回答

我会先判断问题出在检索还是生成。先看知识库里有没有答案，再看切片有没有截断，最后看 sources 的分数和内容。如果召回不准，就调 chunk、Top K 和阈值，再考虑换模型、混合检索或者加 rerank。

---

## 21. 为什么前端上传和删除后要自动刷新列表？

### 标准回答

上传或删除成功后，服务器端的知识库文件集合已经发生变化。如果页面不刷新列表，用户看到的状态会与后端不一致。当前前端在操作成功后再次调用 `GET /documents`，确保页面展示的是最新状态。删除时还增加了确认框和按钮禁用，避免误删与重复提交。

### 口语版回答

后端文件变了，页面也要马上同步。否则上传成功了列表里看不到，或者删掉了页面还显示着。删除时我还加了确认和禁用按钮，避免误操作和重复点击。

---

## 22. 为什么当前项目选择本地 FAISS，而不是直接使用向量数据库？

### 标准回答

当前项目目标是学习 RAG 的完整工程流程。FAISS 部署简单，不需要额外启动数据库服务，适合本地演示和小规模知识库。它能帮助我先理解 embedding、索引构建、相似度检索和来源追踪。后续如果要支持更大规模数据、持久化、多用户和元数据过滤，可以迁移到专门的向量数据库。

### 口语版回答

我先用 FAISS 是因为本地就能跑，适合把 RAG 主流程做通，不用先搭一套数据库。以后如果数据量更大、要持久化或做多用户，再换向量数据库更合适。
