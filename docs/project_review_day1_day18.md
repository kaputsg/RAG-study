# RAG-study Day 1-Day 18 学习复盘

这份复盘用于总结 RAG-study 从 Day 1 到 Day 18 的学习路径、阶段成果、项目边界和后续规划。内容基于当前项目已有能力整理，不写虚假的上线结果。

---

## 1. 项目阶段划分

### 第一阶段：DeepSeek API 与 Python 后端基础

完成了 DeepSeek API 调用封装、环境变量读取和基础异常处理。

学到的是：AI 应用不能把 API Key 写死在代码里，需要用 `.env` 管理配置；模型调用也需要独立封装，方便重试、替换和排错。

### 第二阶段：Embedding、FAISS、RAG 原型

完成了本地 `.txt` 文档读取、chunk 切分、BGE embedding、FAISS 索引构建和基础检索问答。

学到的是：RAG 的核心不是“让模型直接回答”，而是先把本地资料转成可检索的向量，再把相关片段交给模型。

### 第三阶段：FastAPI 后端服务化

完成了 `/ask`、`/health` 等基础接口，让 RAG 能力从脚本变成后端服务。

学到的是：后端接口需要明确请求和响应结构，也需要处理空问题、模型异常和跨域访问等问题。

### 第四阶段：Vue 前端对接

完成了前端问题输入、问答提交、answer 展示和 sources 展示。

学到的是：一个 AI 后端要真正可用，还需要前端把请求状态、错误信息和结果展示清楚。

### 第五阶段：文档上传/删除管理

完成了文档列表、上传 `.txt`、删除文档，以及上传/删除后自动刷新列表和重建索引。

学到的是：知识库内容变化后，文件系统、索引和前端状态必须保持一致。

### 第六阶段：检索质量、日志、评估

完成了 retrieval_info 展示、问答日志和基础评估问题集。

学到的是：RAG 的错误可能出在检索阶段，也可能出在生成阶段；需要通过 sources、retrieval_info、日志和测试问题分析。

### 第七阶段：索引持久化与 manifest

完成了 FAISS 索引持久化和 manifest 知识库变更检测。

学到的是：持久化可以减少重复构建，但必须判断知识库是否变化，否则可能加载到过期索引。

### 第八阶段：部署准备与 Docker

完成了部署准备文档、Dockerfile 和 docker-compose 后端容器化初步实现。

学到的是：Docker 可以提高运行环境的一致性，但后端容器化不等于项目已经正式上线。

### 第九阶段：演示、简历、作品包装

完成了最终验收、演示脚本、项目讲解稿、简历描述和社交平台文案整理。

学到的是：项目不仅要能跑，还要能清楚讲出目标、流程、亮点、边界和后续优化方向。

## 3. 每个阶段学到了什么

- API 调用阶段：学会把模型服务封装成独立模块，而不是散落在业务代码里。
- 文档处理阶段：理解 chunk 切分会影响召回质量和上下文完整性。
- 向量检索阶段：理解 BGE 负责生成向量，FAISS 负责检索向量。
- RAG 组合阶段：理解模型回答质量依赖检索质量。
- 后端接口阶段：理解接口需要有清晰的输入输出和错误处理。
- 前端对接阶段：理解用户体验包括 loading、error、引用展示和状态同步。
- 文档管理阶段：理解上传和删除不仅是文件操作，还会影响索引。
- 日志评估阶段：理解 RAG 项目需要可观察和可复盘。
- 持久化阶段：理解运行效率和数据一致性需要一起考虑。
- Docker 阶段：理解环境复现是部署准备的一部分。
- 包装阶段：理解项目表达要真实，不能把学习原型说成正式产品。

## 5. 遇到的问题与解决方式

**问题：直接调用大模型无法回答本地资料问题**

解决方式：引入 RAG 流程，先检索本地知识库，再调用 DeepSeek API 生成回答。

**问题：整篇文档检索粒度太粗**

解决方式：把 txt 文档切成 chunks，并保留 source 和 chunk_index。

**问题：用户难以判断答案依据**

解决方式：返回 sources，展示文件名、片段位置、相似度和原始内容。

**问题：检索结果不一定可靠**

解决方式：增加 similarity_threshold、retrieval_info 和未知问题拒答逻辑。

**问题：上传和删除文档后索引可能不同步**

解决方式：在文档变化后重建索引，并刷新前端文档列表。

**问题：后端重启重复构建索引**

解决方式：增加 FAISS 索引持久化。

**问题：持久化索引可能过期**

解决方式：增加 manifest 变更检测，知识库变化时自动重建。

**问题：项目运行环境复现不方便**

解决方式：整理部署文档，并做后端 Docker 容器化初步实现。

## 6. 当前项目能力边界

- 支持本地 UTF-8 `.txt` 文档知识库。
- 支持基于 BGE 和 FAISS 的语义检索。
- 支持 DeepSeek API 基于上下文生成回答。
- 支持 FastAPI 后端接口和 Vue 前端页面。
- 支持 answer、sources、retrieval_info 展示。
- 支持文档上传、列表和删除。
- 支持上传/删除后自动重建索引。
- 支持问答日志、基础评估脚本、索引持久化和 manifest 检测。
- 支持后端 Docker 容器化初步运行。

---

## 7. 当前项目不足

- 只支持 UTF-8 `.txt` 文档。
- chunk 切分是固定长度，不是语义切分。
- 上传和删除后仍是全量重建索引。
- 没有多用户权限和数据隔离。
- 没有数据库后台。
- 没有混合检索和 rerank。
- 评估集还比较基础，没有形成完整指标体系。
- Docker 只覆盖后端初步容器化，没有完整线上部署链路。

---

## 8. 后续二阶段规划

1. 扩展文档解析：规划接入 PDF/Word 等常见文档格式。
2. 优化 chunk 策略：尝试按段落、标题或语义切分。
3. 提升检索质量：加入 rerank、混合检索和更系统的评估问题集。
4. 优化索引更新：从全量重建逐步改为增量更新。
5. 增加基础权限：区分不同用户或不同知识库。
6. 增强部署能力：补充前端构建、反向代理、环境变量管理和安全检查。
7. 完善日志分析：统计低置信度问题、拒答案例和高频失败原因。

## 9. 适合写进学习总结的话

通过 RAG-study，我从单纯调用大模型 API，逐步实践了一个本地知识库问答系统的完整链路：文档处理、向量化、检索、上下文生成、后端接口、前端展示、日志评估、索引持久化和部署准备。这个过程让我认识到 AI 应用开发不仅是模型调用，还包括数据处理、检索质量、可解释性、可测试性和系统边界控制。
