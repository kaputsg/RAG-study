# RAG-study 面试追问训练文档

这份文档用于准备 RAG-study 项目的面试追问。表达定位是大二软件工程学生：重点讲清楚自己做了什么、为什么这样做、目前边界在哪里，不把项目包装成已经上线或商用的系统。

---

## 1. 你这个项目是做什么的？

**面试官可能怎么问**

你这个 RAG-study 项目主要解决什么问题？和普通聊天机器人有什么区别？

**推荐回答**

RAG-study 是一个本地知识库 RAG 问答原型。用户可以上传 UTF-8 编码的 `.txt` 文档，系统会把文档切成 chunks，使用 `BAAI/bge-small-zh-v1.5` 生成 embedding，再用 FAISS 建立本地向量索引。用户提问时，后端先检索相关片段，再把片段作为上下文交给 DeepSeek API 生成回答。前端会展示 answer、sources 和 retrieval_info，方便核对回答依据。

**口语版回答**

它不是单纯把问题丢给大模型，而是先从我本地的 txt 知识库里找相关内容，再让模型基于这些内容回答。页面上还能看到引用来源和检索分数，方便判断答案是不是有依据。

**容易踩坑的回答**

这是一个智能问答平台，什么文件都能问，也可以直接商用。

**可以继续补充的点**

当前只支持 `.txt` 文档，适合本地学习和演示；后续可以扩展 PDF/Word、rerank、混合检索和权限控制。

---

## 2. 为什么做 RAG，而不是直接调用大模型？

**面试官可能怎么问**

你为什么不直接调用 DeepSeek API，让模型自己回答？

**推荐回答**

直接调用大模型时，模型不知道我的本地资料内容，而且回答依据不容易追踪。RAG 的思路是先检索本地知识库，把相关片段作为上下文提供给模型，这样回答更贴近指定资料。这个项目还返回 sources 和 retrieval_info，可以看到命中了哪些文档片段、相似度多少，便于调试和核对。

**口语版回答**

直接问大模型，它不一定知道我的本地资料，也可能凭印象回答。RAG 是先查资料再回答，更适合做“基于自己知识库”的问答。

**容易踩坑的回答**

RAG 可以保证模型永远不会胡编。

**可以继续补充的点**

RAG 只能降低幻觉风险，不能完全消除幻觉；检索不准、上下文不足或模型理解偏差都可能造成错误。

## 3. RAG 的完整流程是什么？

**面试官可能怎么问**

从用户上传文档到用户提问，完整链路怎么走？

**推荐回答**

文档进入知识库后，系统读取 `.txt` 内容，按固定长度切分成 chunks，并保留 source 和 chunk_index。随后用 BGE 模型把 chunks 转成 embedding，写入 FAISS 索引。用户提问时，问题也会被转成 embedding，在 FAISS 中检索相似 chunks，低于阈值的结果会被过滤。RAGService 把保留下来的片段拼成 context，再调用 DeepSeek API 生成回答，最后返回 answer、sources 和 retrieval_info。

**口语版回答**

流程就是：读文档、切片、向量化、建索引；提问时把问题也向量化，检索相关片段，再把片段交给大模型生成答案。

**容易踩坑的回答**

RAG 就是把所有文档一次性放进 prompt。

**可以继续补充的点**

项目里上传和删除文档后会重建索引，启动时也会通过 manifest 判断知识库是否变化。

---

## 4. Embedding 是什么？

**面试官可能怎么问**

你说用了 embedding，embedding 在这里是什么意思？

**推荐回答**

Embedding 是把文本转换成一组数字向量，用来表示文本语义。这样系统就可以比较两个文本在语义空间里的接近程度。项目中，知识库 chunks 和用户问题都用同一个 BGE 模型生成 embedding，然后通过 FAISS 做相似度检索。

**口语版回答**

可以理解为把一句话变成一串数字。意思相近的文本，向量距离也会比较近，所以可以用来找相关资料。

**容易踩坑的回答**

Embedding 就是关键词匹配。

**可以继续补充的点**

Embedding 更偏语义匹配，但不代表一定理解准确；模型选择和文本切分都会影响效果。

---

## 5. 你用的是什么向量模型？

**面试官可能怎么问**

你的向量是怎么生成的？用了哪个模型？

**推荐回答**

项目使用 `BAAI/bge-small-zh-v1.5` 生成中文文本 embedding。选择它主要是因为它对中文语义检索比较友好，模型体积相对小，适合本地学习项目运行。项目没有追求最大模型，而是优先把 RAG 的完整流程做通。

**口语版回答**

我用的是 BGE 的中文 small 版本，主要考虑中文效果和本地运行成本之间的平衡。

**容易踩坑的回答**

我用了最强的向量模型，所以检索一定准确。

**可以继续补充的点**

后续可以对比更大的 BGE、m3e、text2vec 或云端 embedding 服务，用评估集比较命中率。

---

## 6. BGE-small-zh-v1.5 的优缺点是什么？

**面试官可能怎么问**

为什么选 small 版本？它有什么限制？

**推荐回答**

优点是中文语义检索适配较好，模型相对轻量，适合本地开发和学习，启动和推理成本比大模型低。缺点是表达能力和复杂语义判断不如更大的 embedding 模型，遇到长文本、跨段推理或专业术语较多的内容时，检索效果可能不稳定。

**口语版回答**

它的好处是轻量、中文效果还可以，适合我这种本地项目。缺点是 small 版本能力有限，复杂问题可能检索不到最准确的片段。

**容易踩坑的回答**

small 版本没有缺点，只要用了 BGE 就够了。

**可以继续补充的点**

可以通过调 chunk 参数、增加评估集、引入 rerank 或换更强 embedding 模型来优化。

---

## 7. FAISS 在项目里负责什么？

**面试官可能怎么问**

FAISS 是大模型吗？它在项目里做什么？

**推荐回答**

FAISS 不是大模型，它负责本地向量索引和相似度检索。BGE 生成 embedding 后，FAISS 保存这些向量，并在用户提问时返回最相似的 chunks。项目使用本地 FAISS 是为了降低部署复杂度，先理解向量检索的基本流程。

**口语版回答**

BGE 负责把文字变成向量，FAISS 负责存向量和查相似向量。

**容易踩坑的回答**

FAISS 负责理解问题并生成答案。

**可以继续补充的点**

FAISS 适合本地和小规模原型；数据量大、需要权限和元数据过滤时，可以考虑向量数据库。

---

## 8. BGE 和 FAISS 的区别是什么？

**面试官可能怎么问**

BGE 和 FAISS 都和向量有关，它们分别负责什么？

**推荐回答**

BGE 是 embedding 模型，负责把文本转换成语义向量；FAISS 是向量检索库，负责存储向量和查找相似向量。两者是上下游关系：没有 BGE 就没有文本向量，没有 FAISS 就缺少高效的向量检索结构。

**口语版回答**

BGE 是“翻译器”，把文字翻成向量；FAISS 是“检索工具”，在向量里找最像的内容。

**容易踩坑的回答**

BGE 和 FAISS 是同一种东西。

**可以继续补充的点**

项目中还会保留 chunk 的原始文本和来源元数据，检索到向量后才能展示 sources。

---

## 9. 为什么要做 chunk 切分？

**面试官可能怎么问**

为什么不直接把整篇文档向量化？

**推荐回答**

整篇文档可能包含多个主题，直接生成一个向量会丢失局部语义，检索时很难定位到具体答案。切成 chunks 后，每个片段语义更集中，检索结果也更容易作为上下文交给模型，同时 sources 可以定位到具体片段。

**口语版回答**

文档太长时，一个向量代表不了所有细节。切片以后，系统更容易找到真正相关的那几段。

**容易踩坑的回答**

chunk 越小越好，越细越准确。

**可以继续补充的点**

chunk 太小会丢上下文，太大又会混入无关内容，所以需要结合评估问题调参。

---

## 10. chunk_size 和 chunk_overlap 有什么影响？

**面试官可能怎么问**

chunk_size 和 chunk_overlap 怎么影响检索？

**推荐回答**

chunk_size 决定每个片段的长度。太小容易让语义不完整，太大容易引入无关信息。chunk_overlap 用来保留相邻片段之间的重叠内容，减少句子或段落被切断造成的信息丢失。RAG-study 当前使用固定长度切分，适合学习阶段，后续可以改成按段落或语义切分。

**口语版回答**

size 控制一段有多长，overlap 控制相邻片段重叠多少。它们会影响检索准不准，也影响传给模型的上下文质量。

**容易踩坑的回答**

chunk_size 只影响速度，不影响答案质量。

**可以继续补充的点**

可以用基础评估问题集观察不同参数下 sources 是否命中正确文档。

---

## 11. sources 引用来源有什么用？

**面试官可能怎么问**

为什么要在前端显示 sources？

**推荐回答**

sources 用于提高回答的可追踪性。它记录了答案参考的文件名、chunk_index、相似度和原始片段。用户或开发者可以核对答案是否真的来自知识库，也可以在检索不准时定位问题。

**口语版回答**

我不希望页面只给一个答案，还要告诉用户这个答案参考了哪份资料、哪一段。

**容易踩坑的回答**

有 sources 就说明答案一定正确。

**可以继续补充的点**

sources 是判断依据的重要辅助，但还需要人工核对和评估集验证。

---

## 12. retrieval_info 有什么用？

**面试官可能怎么问**

retrieval_info 和 sources 有什么区别？

**推荐回答**

sources 更偏具体引用片段，retrieval_info 更偏整体检索质量。它可以展示是否命中、最高分、来源数量、置信度等信息，帮助判断这次回答的依据是否充足。对调试 RAG 很有帮助，因为很多问题不是生成模型错，而是检索阶段没找到正确上下文。

**口语版回答**

sources 告诉我引用了哪些片段，retrieval_info 告诉我这次检索整体质量怎么样。

**容易踩坑的回答**

retrieval_info 是模型最终答案的准确率。

**可以继续补充的点**

后续可以把 retrieval_info 和日志结合，统计问题命中率、低分问题和失败案例。

---

## 13. 为什么要做未知问题拒答？

**面试官可能怎么问**

为什么不让模型尽量回答所有问题？

**推荐回答**

如果知识库没有相关资料，强行让模型回答会增加幻觉风险。项目通过相似度阈值过滤低相关结果，如果没有合格片段，就返回未找到相关信息或低置信度提示。这比编造答案更符合知识库问答的定位。

**口语版回答**

知识库没有资料时，我宁愿系统说不知道，也不要让模型硬编。

**容易踩坑的回答**

模型很强，所以不知道也可以自己推理。

**可以继续补充的点**

拒答阈值需要通过测试问题调参，阈值太高可能误拒答，太低可能引入无关上下文。

---

## 14. RAG 能不能完全消除幻觉？

**面试官可能怎么问**

用了 RAG 后，是不是就不会胡编了？

**推荐回答**

不能。RAG 可以降低幻觉风险，但不能完全消除。原因包括检索结果不准、chunk 切分不合理、上下文不足、模型理解错误，以及 prompt 约束不够强。RAG-study 通过 sources、retrieval_info、阈值过滤和未知问题拒答来降低风险，但仍然需要人工核对和评估。

**口语版回答**

不能保证完全没有幻觉。RAG 只是让模型有资料可参考，但资料找错了或者模型理解错了，答案还是可能错。

**容易踩坑的回答**

RAG 的答案一定比大模型直接回答正确。

**可以继续补充的点**

可以通过更好的检索、rerank、严格 prompt、评估集和人工验收继续降低错误率。

---

## 15. 上传文档后为什么要重建索引？

**面试官可能怎么问**

文件上传到目录里了，为什么还要重建 FAISS？

**推荐回答**

上传文件只是改变了磁盘上的知识库文件，FAISS 索引不会自动知道新文件内容。系统必须重新读取文档、切分 chunks、生成 embedding，并把新向量写入索引，否则新文档无法被检索到。

**口语版回答**

文件放进去了，不代表检索系统已经认识它。要重新切片、向量化、建索引，它才能被问到。

**容易踩坑的回答**

只要文件在 data 目录里，FAISS 会自动检索。

**可以继续补充的点**

当前是全量重建，简单可靠；文档多时可以做增量索引。

---

## 16. 删除文档后为什么要重建索引？

**面试官可能怎么问**

删除文件后为什么也要重建？

**推荐回答**

如果只删除原文件，不更新索引，FAISS 中可能还保留旧文件对应的向量，检索时会返回已经不存在的内容。重建索引可以让文件系统和向量索引保持一致。

**口语版回答**

不重建的话，文件删了，但索引里可能还有旧片段，用户还能搜到不存在的资料。

**容易踩坑的回答**

删除文件不会影响索引，所以不用处理。

**可以继续补充的点**

后续可以记录文档 ID，实现更细粒度的增量删除。

---

## 17. FAISS 索引持久化解决了什么问题？

**面试官可能怎么问**

为什么要持久化索引？每次启动重建不行吗？

**推荐回答**

每次启动都重建索引会重复读取文档、生成 embedding 和构建 FAISS，启动时间会变长。索引持久化后，后端可以优先加载已有索引和 chunks，减少重复计算。对于本地项目来说，它体现了部署和运行效率意识。

**口语版回答**

持久化就是把已经建好的索引存下来，下次启动能直接用，避免每次从零开始算。

**容易踩坑的回答**

持久化后就不需要检查知识库变化。

**可以继续补充的点**

持久化必须配合 manifest 变更检测，否则可能加载到过期索引。

---

## 18. manifest 变更检测解决了什么问题？

**面试官可能怎么问**

manifest 是做什么的？为什么不直接加载持久化索引？

**推荐回答**

manifest 用来记录知识库文件状态，例如文件名、大小或修改时间等信息。后端启动时可以比较当前知识库和上次保存的 manifest，如果文件发生变化，就重建索引；如果没有变化，就加载持久化索引。它解决的是索引和文件内容可能不一致的问题。

**口语版回答**

manifest 像一个知识库清单。它帮我判断现在的文件和上次建索引时是不是一样。

**容易踩坑的回答**

manifest 是用来保存用户问题的。

**可以继续补充的点**

更严格的做法可以记录文件 hash，减少只看时间戳带来的误判。

---

## 19. FastAPI 在项目里负责什么？

**面试官可能怎么问**

FastAPI 在你的系统中承担什么职责？

**推荐回答**

FastAPI 是后端接口层，负责接收前端请求、调用 RAGService、返回结构化响应。当前接口包括 `GET /`、`GET /health`、`POST /ask`、`GET /documents`、`POST /documents/upload` 和 `DELETE /documents/{filename}`。它还负责文件上传校验、删除校验、异常返回和 CORS 配置。

**口语版回答**

FastAPI 是前端和 RAG 逻辑之间的桥。前端点按钮，实际的问答、上传、删除都通过 FastAPI 接口触发。

**容易踩坑的回答**

FastAPI 负责生成 embedding。

**可以继续补充的点**

FastAPI 只是接口层，具体检索和生成逻辑封装在 RAGService、vector_store、document_loader 等模块里。

## 20. Vue 在项目里负责什么？

**面试官可能怎么问**

前端除了输入问题，还做了什么？

**推荐回答**

Vue 前端负责提供交互界面，包括输入问题、提交问答、展示 answer、sources、retrieval_info、上传 `.txt` 文档、展示文档列表和删除文档。上传和删除成功后，前端会自动刷新文档列表，保证页面状态和后端一致。

**口语版回答**

Vue 主要负责把后端能力做成可操作页面，不只是一个输入框，还包括文档管理和检索信息展示。

**容易踩坑的回答**

前端只负责美化页面，和核心功能没关系。

**可以继续补充的点**

前端通过 Fetch API 调用后端，API 地址来自 `VITE_API_BASE_URL`。

## 21. Docker 化解决了什么问题？

**面试官可能怎么问**

你为什么要做 Docker？它是不是表示项目已经部署上线了？

**推荐回答**

Docker 化主要解决后端运行环境一致性问题。项目通过 Dockerfile 和 docker-compose 初步实现 FastAPI 后端容器化，方便在本地用相同依赖环境启动后端。但这不代表已经上线，也不包含前端 Nginx、HTTPS、域名、鉴权和监控。

**口语版回答**

Docker 是为了让后端环境更容易复现，不是说项目已经正式上线了。

**容易踩坑的回答**

用了 Docker 就等于项目已经可以商用部署。

**可以继续补充的点**

后续如果继续做部署，可以补充前端构建、反向代理、环境变量管理和安全检查。

## 22. 这个项目目前有哪些不足？

**面试官可能怎么问**

你觉得项目现在最明显的问题是什么？

**推荐回答**

当前项目定位是本地学习原型，主要不足包括：只支持 UTF-8 `.txt`，不支持 PDF/Word；chunk 切分还是固定长度；上传和删除后采用全量重建索引，文档多时效率会下降；没有多用户权限、数据库后台、增量索引、rerank 和系统化评估平台。

**口语版回答**

它现在是把 RAG 主流程做通了，但还不是一个成熟产品。文件格式、索引更新效率、权限、安全和评估都还有优化空间。

**容易踩坑的回答**

这个项目已经比较完整，没有明显不足。

**可以继续补充的点**

可以强调“知道边界”本身也是项目表达的一部分。

## 23. 后续怎么优化？

**面试官可能怎么问**

如果继续做，你下一步会怎么改？

**推荐回答**

我会按优先级优化：第一，扩展文档解析能力，比如 PDF/Word；第二，改进 chunk 策略，尝试按段落或语义切分；第三，引入 rerank 或混合检索提升召回质量；第四，把全量重建优化为增量更新；第五，补充更系统的评估集、错误案例分析和基础权限控制。

**口语版回答**

我会先把文档格式和检索质量做好，再考虑增量索引、评估和权限这些工程化能力。

**容易踩坑的回答**

下一步直接做成大平台。

**可以继续补充的点**

优化路线要和当前项目规模匹配，不要直接跳到复杂系统。

## 25. 你在这个项目里最大的收获是什么？

**面试官可能怎么问**

这个项目对你最大的提升是什么？

**推荐回答**

最大的收获是把 AI 应用从单点 API 调用扩展成了完整链路。我从 DeepSeek API 调用、环境变量管理、文档读取、chunk 切分、BGE embedding、FAISS 检索、RAGService 封装，到 FastAPI 接口、Vue 前端、日志、评估、索引持久化、manifest 检测和 Docker 后端容器化都实践了一遍。这个过程让我更理解 RAG 不只是调模型，还包括检索质量、可解释性、可测试性和运行维护。

**口语版回答**

我最大的收获是知道了一个 AI 应用不是只调 API。要让它真正能用，还要做资料处理、检索、接口、页面、日志、评估和部署准备。

**容易踩坑的回答**

我已经完全掌握了 RAG 和大模型应用开发。

**可以继续补充的点**

可以结合自己是大二学生，强调“系统学习并实践了完整流程”，不要用过度包装的表达。
